## Overview

Returns the current status and key timestamps of an order created with **the same API key**. Use it to poll for the outcome, to reconcile after a missed webhook, or to confirm a webhook before you fulfil.

| | |
|---|---|
| **API key** | Required |
| **Signature** | Required. Sign the request with an empty body; see the [Signature Generation Guide](/api-reference/signature-guide). |

## Headers

<ParamField header="Authorization" type="string" required>
  `Bearer mk_live_...`, the **same API key** that created the order.
</ParamField>

<ParamField header="X-C2C-Timestamp" type="string" required>
  Unix time in seconds when the request was signed.
</ParamField>

<ParamField header="X-C2C-Signature" type="string" required>
  Signature over `{timestamp}\nGET\n/api/merchant/orders/{id}/status\ne3b0c44298fc1c149afbf4c8996fb92427ae41e4649b934ca495991b7852b855`. The last part is the SHA-256 of the empty body.
</ParamField>

## Path parameters

<ParamField path="id" type="uuid" required>
  The `orderId` returned by [Create deposit](/api-reference/endpoints/create-deposit) or [Create withdrawal](/api-reference/endpoints/create-withdrawal), also present in webhooks.

  <Note>
    Orders can only be looked up by `orderId`. Your `merchantOrderRef` and C2C's `orderReference` can't be used here, so always store the `orderId`.
  </Note>
</ParamField>

    <ResponseField name="status" type="string">

    <ResponseField name="amount" type="number">
      Order amount in the order currency.
    </ResponseField>
    <ResponseField name="queuedAt" type="string">
      ISO 8601 UTC time the order entered the queue (creation time for withdrawals).
    </ResponseField>
    <ResponseField name="confirmedAt" type="string | null">
      When the order completed successfully, otherwise `null`.
    </ResponseField>
    <ResponseField name="cancelledAt" type="string | null">
      When the order was explicitly cancelled, otherwise `null`. It stays `null` for `Rejected`, `Expired` and `CancelledTimeout`; check `status` instead.
    </ResponseField>
  </Expandable>
</ResponseField>

## Status values

| Status | Applies to | Meaning | Final? |
|--------|-----------|---------|--------|
| `Queued` | Deposit | Created. The customer hasn't chosen a wallet on the payment page yet. | No |
| `AwaitingCustomerPayment` | Deposit | Wallet chosen and account shown. Waiting for the customer to pay and submit the transaction digits. | No |
| `AwaitingMemberConfirmation` | Deposit | Customer submitted payment. Waiting for the member to verify receipt. | No |
| `AwaitingMemberPayout` | Withdrawal | Waiting for the member to send the payout. | No |
| `ManualReview` | Both | Escalated to C2C operations, for example a member confirmation or payout window passed. Resolved by C2C to `Completed` or `Cancelled`. | No |
| `Completed` | Both | **Success.** Funds received (deposit) or paid out (withdrawal). | **Yes, success** |
| `Rejected` | Both | The member rejected the order, for example because no matching payment was received. | **Yes, failed** |
| `Expired` | Deposit | The customer didn't pay before the payment page expired. | **Yes, failed** |
| `CancelledTimeout` | Deposit | No checkout activity before the queue timeout. | **Yes, failed** |
| `Cancelled` | Both | Cancelled by C2C or the member. | **Yes, failed** |
| `CancelledAuto` | Both | Cancelled automatically by the system. | **Yes, failed** |

<Accordion title="Legacy statuses (older orders only)">
  Orders created by earlier versions of the platform can also report `Assigned` (in progress), `Frozen` (in progress, past the member's freeze window) and `Confirmed` (**success**, equivalent to `Completed`). Treat `Confirmed` as success if you see it.
</Accordion>

<Warning>
  Fulfil a deposit or record a payout **only** on `Completed` (or legacy `Confirmed`). `ManualReview` isn't a failure: don't refund or re-pay the customer until C2C resolves the order.
</Warning>

## Polling guidelines

- Prefer [webhooks](/guides/webhooks) and poll as a fallback or to reconcile.
- Poll every **5–10 seconds** while the customer is on the payment page, then back off (for example every minute) for orders waiting on a member.
- Stop polling once the status is final.
- Each API key has a [rate limit](/api-reference/rate-limits) of 100 requests per minute across all merchant endpoints. Don't poll many orders in tight loops.
- After C2C resolves a `ManualReview` order, no webhook is sent, so keep polling those orders at a low frequency until they are final.

```javascript Node.js
const FINAL = new Set(['Completed', 'Confirmed', 'Rejected', 'Expired', 'CancelledTimeout', 'Cancelled', 'CancelledAuto']);
const SUCCESS = new Set(['Completed', 'Confirmed']);

async function waitForOutcome(orderId, { intervalMs = 5000, timeoutMs = 30 * 60 * 1000 } = {}) {
  const deadline = Date.now() + timeoutMs;
  while (Date.now() < deadline) {
    const { status } = await getOrderStatus(orderId);
    if (FINAL.has(status)) return { status, success: SUCCESS.has(status) };
    await new Promise((r) => setTimeout(r, intervalMs));
  }
  return { status: 'Pending', success: false }; // keep reconciling later
}
```

## Error responses

| Status | When | Body |
|--------|------|------|
| `401` | API key missing, invalid or revoked | Empty body |
| `401` | Signature rejected (when enforced for this endpoint) | `{"success": false, "error", "code", "traceId"}` |
| `404` | No order with this ID **for this API key**, including orders created with a different key | `{"error": "Order not found."}` |
| `429` | Rate limit exceeded | Empty body |
