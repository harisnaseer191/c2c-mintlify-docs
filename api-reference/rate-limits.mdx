## Limits

| Property | Value |
|----------|-------|
| Endpoints | All merchant API endpoints (`/api/merchant/orders/**`) |
| Limit | **100 requests per minute, per API key** |
| Window | Fixed one-minute window |
| Scope | Each API key has its own budget. One key's traffic, or another merchant's, never uses up another key's allowance. Status polling counts toward the limit. |
| Over the limit | `429 Too Many Requests` with an **empty body**. Requests aren't queued. |

Requests rejected for a missing or invalid API key (`401`) are rejected before the rate limit applies.

<Note>
  `429` responses don't include `Retry-After` or `X-RateLimit-*` headers. The window resets at most one minute after it started.
</Note>

## Handling `429`

A `429` means the request was **not processed**, so retrying it is safe. For order creation, keep the same `Idempotency-Key` and sign the retry again.

```javascript Node.js
async function withRateLimitRetry(send, maxAttempts = 5) {
  for (let attempt = 0; attempt < maxAttempts; attempt++) {
    const response = await send(); // send() must re-sign the request on every call
    if (response.status !== 429) return response;
    const delayMs = Math.min(60_000, 2 ** attempt * 2_000) + Math.random() * 1_000; // backoff + jitter
    await new Promise((r) => setTimeout(r, delayMs));
  }
  throw new Error('Rate limited: gave up after retries');
}
```

## Staying under the limit

- Use [webhooks](/guides/webhooks) instead of polling wherever possible.
- When polling [order status](/api-reference/endpoints/query-order-status), poll every 5–10 seconds while a customer is actively paying, and less often after that. Stop when the status is final.
- Don't poll [wallet balance](/api-reference/endpoints/query-balance) in a loop. Read it when you need it, for example before a batch of payouts.
- Spread bulk payouts out over time instead of sending them in a burst.
