## Overview

C2C sends an HTTP `POST` to your callback URL when an order reaches a **final** outcome, so you don't have to poll. Webhooks are a **notification**. The [order status endpoint](/api-reference/endpoints/query-order-status) remains the source of truth.

```text
Order becomes final ──▶ C2C updates order ──▶ POST {callbackUrl}  (signed)
                                                     │
                                         your endpoint returns 2xx
                                                     │
                                  non-2xx / unreachable → retried later
```

## Configuring the callback URL

| Source | Priority |
|--------|----------|
| `callbackUrl` in the [create order](/api-reference/endpoints/create-deposit) request | Used when provided |
| Default callback URL in **Merchant Portal → Settings** (needs the Settings permission) | Used when the request omits `callbackUrl` |

The URL is **fixed when the order is created**. Changing your portal setting later doesn't affect orders that already exist. If neither URL is set, no webhook is sent for that order.

Use a publicly reachable endpoint that accepts `POST` with a JSON body. `callbackUrl` must be an absolute `http://` or `https://` URL (any other scheme is rejected with `400`). Use **HTTPS** in production.

The URL must resolve to a **public internet address**. Loopback, private, link-local (including `169.254.169.254`) and similar addresses are refused when C2C delivers the webhook: that delivery fails and is retried and recorded like any other failure. Redirects aren't followed, so point the URL at the final endpoint.

## Events

Webhooks are sent for **final outcomes only**.

| `eventType` | Sent when | `status` in payload |
|-------------|-----------|---------------------|
| `order.completed` | The order settled: the member confirmed receipt of a deposit or the payout of a withdrawal, or C2C operations resolved the order as confirmed. **Safe to fulfil.** | `Completed` (or legacy `Confirmed`) |
| `order.failed` | The order ended without settlement: the member rejected it, the checkout link expired, no member became available in time, or it was cancelled (by C2C operations or automatically) | `Rejected`, `Expired`, `CancelledTimeout`, `Cancelled` or `CancelledAuto` |

Example `reason` values on `order.failed`: `Checkout expired before payment`, `No eligible member became available in time`, the member's rejection reason, or the resolution note from C2C operations.

<Note>
  `ManualReview` doesn't send a webhook. The order isn't final: it's being handled by C2C operations, and you can see it through [status inquiry](/api-reference/endpoints/query-order-status) (status `ManualReview`). You receive `order.completed` or `order.failed` once it is resolved. Don't refund or re-pay the customer in the meantime.
</Note>

<Warning>
  An order that failed can later be **confirmed by C2C operations**, for example after a dispute is resolved. You then receive `order.completed` after the earlier `order.failed`. Always act on the **latest** event, and confirm with a [status query](/api-reference/endpoints/query-order-status).
</Warning>

## Request format

```http
POST /webhooks/c2c HTTP/1.1
Content-Type: application/json; charset=utf-8
X-C2C-Event: order.completed
X-C2C-Signature: sha256=5d1f0c2e8b7a...
X-C2C-Key-Prefix: a1b2c3d4
X-C2C-Delivery-Id: 48213
X-C2C-Timestamp: 1791461502
```

| Header | Description |
|--------|-------------|
| `X-C2C-Event` | Event type, the same as `eventType` in the body |
| `X-C2C-Signature` | `sha256=` + lowercase hex HMAC-SHA256 of the **raw request body**, keyed with your API key's **signing secret** (`sksec_...`) |
| `X-C2C-Key-Prefix` | Which of your API keys signed it: the 8 characters after `mk_live_` in that key (also shown in the Merchant Portal) |
| `X-C2C-Delivery-Id` | ID of this delivery. Automatic retries of a delivery keep the same ID; a [resend](#resends-by-c2c-operations) gets a new one. Quote it when you contact C2C support. |
| `X-C2C-Timestamp` | Unix time (seconds) when **this attempt** was sent. It changes on every retry. |

<Note>
  `X-C2C-Delivery-Id` and `X-C2C-Timestamp` are informational and are **not** covered by the signature. Only the raw body is signed. Don't use them as the only basis for a security decision.
</Note>

## Verifying the signature

Webhooks are signed with your API key's **signing secret** (`sksec_...`), the same secret you use to [sign API requests](/api-reference/signature-guide). No separate webhook secret is needed.

Which key's secret is used:

1. The API key that **created the order**, while that key is still active.
2. Otherwise (the key was revoked or rotated), your **newest active** API key.

`X-C2C-Key-Prefix` names the key, so if you hold several keys, or are mid-rotation, you can pick the matching secret instead of trying each one.

<Note>
  Every attempt is signed with the secret that is current **at that attempt**. A retry of a webhook first sent before a key rotation arrives signed with your **new** key's secret. Deploy the new secret before the old key is revoked.
</Note>

<Note>
  Legacy API keys issued without a signing secret get webhooks signed with a platform secret and no `X-C2C-Key-Prefix` header. Ask C2C to regenerate the key to switch to per-merchant signing.
</Note>

To verify a webhook:

1. Read the **raw body bytes** before any JSON parsing.
2. Compute `sha256=` + hex(HMAC-SHA256(signingSecret, rawBody)).
3. Compare with `X-C2C-Signature` using a **constant-time** comparison.
4. Reject the request with `401` if they don't match, and don't process it.

<CodeGroup>

```javascript Node.js (Express)
const crypto = require('crypto');
const express = require('express');
const app = express();

function isValidSignature(rawBody, header, secret) {
  const expected = 'sha256=' + crypto.createHmac('sha256', secret).update(rawBody).digest('hex');
  const a = Buffer.from(expected);
  const b = Buffer.from(header || '');
  return a.length === b.length && crypto.timingSafeEqual(a, b);
}

app.post('/webhooks/c2c', express.raw({ type: 'application/json' }), async (req, res) => {
  if (!isValidSignature(req.body, req.get('X-C2C-Signature'), process.env.C2C_SIGNING_SECRET)) {
    return res.sendStatus(401);
  }
  const event = JSON.parse(req.body.toString('utf8'));
  res.sendStatus(200);                 // acknowledge fast
  await processEventOnce(event);       // then handle idempotently (see below)
});
```

```python Python (Flask)

from flask import Flask, request, abort

app = Flask(__name__)

def is_valid_signature(raw_body: bytes, header: str, secret: str) -> bool:

@app.post("/webhooks/c2c")

    if not is_valid_signature(raw, request.headers.get("X-C2C-Signature"), os.environ["C2C_SIGNING_SECRET"]):
        abort(401)
    event = json.loads(raw)
    process_event_once(event)  # idempotent handler
    return "", 200
```

## Responding and retries

- Return any **`2xx`** status to acknowledge the event. The response body is ignored.
- Respond within **5 seconds**. Do the heavy work asynchronously after you acknowledge.
- A non-`2xx` response, a timeout or a connection error counts as a failed delivery.

A failed delivery is retried with exponential backoff, up to **10 attempts** in total:

| After failed attempt | Next attempt in about |
|----------------------|-----------------------|
| 1 | 1 min |
| 2 | 2 min |
| 3 | 4 min |
| 4 | 8 min |
| 5 | 16 min |
| 6 | 32 min |
| 7 | 64 min |
| 8 | 2 h 8 min |
| 9 | 4 h 16 min |
| 10 | not retried; delivery abandoned |

Each retry sends the **identical body** (same `timestamp`) with the same `X-C2C-Delivery-Id`. Retries are processed once a minute, so an attempt can arrive up to a minute after the time shown. After the last attempt, [reconcile with the status endpoint](#reconciliation).

### Newer events replace older ones

If an order produces a newer event while an earlier one is still being retried, the earlier delivery is **superseded**: its retries stop and only the newer event is delivered. For example, if an order fails and C2C operations then resolve it as completed, you receive `order.completed`, and the pending `order.failed` retries stop. A stale outcome never arrives after a newer one.

### Resends by C2C operations

C2C operations can send a webhook again from the admin portal, for example after you fix your endpoint:

- **Retry now** sends a failed delivery again immediately: the same body and the same `X-C2C-Delivery-Id`. Only the latest delivery for an order can be retried.
- **Resend** sends a **new** delivery for the order's current final outcome. It has a new `X-C2C-Delivery-Id` and a new body `timestamp`, but the same `orderId` and `eventType`.

Both are signed with your current signing secret, like any other attempt. Because a resend is a new delivery, deduplicate on the order and its outcome, not on the delivery ID (see below).

## Handling duplicates

You **will** sometimes receive the same event more than once, because of retries, network timeouts and resends by C2C operations. Make your handler idempotent:

```javascript
async function processEventOnce(event) {
  const key = `${event.orderId}:${event.eventType}`;
  if (await alreadyProcessed(key)) return;          // e.g. unique index in your DB

  // Confirm against the source of truth before moving money or goods
  const { status } = await getOrderStatus(event.orderId);
  if (status === 'Completed' || status === 'Confirmed') {
    await fulfilOrder(event.orderId);
  }
  await markProcessed(key);
}
```

- Deduplicate on `orderId` + `eventType`. Don't deduplicate on `X-C2C-Delivery-Id` or the body `timestamp` alone: a resend changes both.
- Ignore duplicate events for orders you have already finalized, but still act on an `order.completed` that follows an earlier `order.failed` (an order resolved by C2C operations).
- Before fulfilling, re-check the status with [Query order status](/api-reference/endpoints/query-order-status). This also protects you if your signing secret is ever exposed.

## Reconciliation

Run a periodic job, for example every 5–15 minutes, that queries the status of every order you created that:

- is not yet final in your system, and
- is older than your expected completion time.

That catches orders still in `ManualReview` and any delivery that never reached you.

## Best practices

<AccordionGroup>
  <Accordion title="Verify every request">
    Reject unsigned or incorrectly signed callbacks with `401` and don't act on them.
  </Accordion>
  <Accordion title="Use HTTPS">
    Your callback URL should use HTTPS with a valid certificate.
  </Accordion>
  <Accordion title="Don't trust the payload alone for money movement">
    Re-check the order status before you credit a customer or mark a payout as done.
  </Accordion>
  <Accordion title="Keep the secret server-side">
    The signing secret verifies webhooks and signs your API requests. Keep it in environment variables or a secret manager, never in code or logs.
  </Accordion>
</AccordionGroup>
