## Overview

The C2C Merchant API uses two credentials, issued together:

| Credential | Format | Used for |
|------------|--------|----------|
| **API key** | `mk_live_` + 32 alphanumeric characters | Identifies your merchant account. Sent as a Bearer token. |
| **Signing secret** | `sksec_` + 40 alphanumeric characters | Signs each request and verifies the [webhooks](/guides/webhooks) C2C sends you. Never sent over the wire. See the [Signature Generation Guide](/api-reference/signature-guide). |

<Warning>
  Both credentials are shown **only once**, when C2C issues them. C2C stores only a hash of your API key and cannot show it to you again. Store both immediately in a secret manager or environment variables, and never expose them in client-side code.
</Warning>

## Getting your credentials

A C2C administrator issues API keys for your merchant account, and each key comes with its own signing secret. In the **Merchant Portal** you can see your keys (name, prefix, status, last used) and revoke a key, but you can't create new ones there. Contact C2C to get a key or to rotate one.

- You can hold **more than one active API key** (for example one per backend service). Each key has its own signing secret.
- Orders and idempotency keys are **scoped to the API key that created them**. A status request made with a different key returns `404`.
- **Regenerating** your API key issues a new key and secret and **revokes every previously active key** on your account.
- A revoked key stops working within about **2 minutes**.

## Authentication method

Send your API key in the `Authorization` header using the Bearer scheme:

```http
Authorization: Bearer mk_live_your_api_key
```

### Required headers

| Header | Required on | Value |
|--------|-------------|-------|
| `Authorization` | All requests | `Bearer mk_live_...` |
| `X-C2C-Timestamp` | All requests | Unix seconds at signing time |
| `X-C2C-Signature` | All requests | `sha256=<hex>`, see the [Signature Generation Guide](/api-reference/signature-guide) |
| `Content-Type` | Requests with a body | `application/json` |
| `Idempotency-Key` | `POST /api/merchant/orders` | Your unique key for this order attempt, up to 100 characters. See [Idempotency](/api-reference/idempotency). |

### Example request

<CodeGroup>
```bash cURL
# TIMESTAMP and SIGNATURE computed as described in the Signature Generation Guide
# (GET request → body hash of the empty string)
curl --request GET \
  --url https://ca-c2c-dev-api.calmsea-c64629ed.uaenorth.azurecontainerapps.io/api/merchant/orders/balance \
  --header "Authorization: Bearer $C2C_API_KEY" \
  --header "X-C2C-Timestamp: $TIMESTAMP" \
  --header "X-C2C-Signature: $SIGNATURE"
```

```javascript Node.js
// signRequest() is defined in the Signature Generation Guide
const path = '/api/merchant/orders/balance';
const response = await fetch(
  `https://ca-c2c-dev-api.calmsea-c64629ed.uaenorth.azurecontainerapps.io${path}`,
  {
    headers: {
      'Authorization': `Bearer ${process.env.C2C_API_KEY}`,
      ...signRequest(process.env.C2C_SIGNING_SECRET, 'GET', path, ''),
    },
  }
);
console.log(response.status, await response.json());
```

```python Python
import os
import requests

# sign_request() is defined in the Signature Generation Guide
path = "/api/merchant/orders/balance"
response = requests.get(
    f"https://ca-c2c-dev-api.calmsea-c64629ed.uaenorth.azurecontainerapps.io{path}",
    headers={
        "Authorization": f"Bearer {os.environ['C2C_API_KEY']}",
        **sign_request(os.environ["C2C_SIGNING_SECRET"], "GET", path, ""),
    },
)
print(response.status_code, response.json())
```

```php PHP
<?php
// signRequest() is defined in the Signature Generation Guide
$path = '/api/merchant/orders/balance';
$signed = signRequest(getenv('C2C_SIGNING_SECRET'), 'GET', $path, '');

$ch = curl_init('https://ca-c2c-dev-api.calmsea-c64629ed.uaenorth.azurecontainerapps.io' . $path);
curl_setopt_array($ch, [
    CURLOPT_RETURNTRANSFER => true,
    CURLOPT_HTTPHEADER => [
        'Authorization: Bearer ' . getenv('C2C_API_KEY'),
        'X-C2C-Timestamp: ' . $signed['X-C2C-Timestamp'],
        'X-C2C-Signature: ' . $signed['X-C2C-Signature'],
    ],
]);
echo curl_exec($ch);
curl_close($ch);
```
</CodeGroup>

A successful call returns `200`:

```json
{
  "data": {
    "availableBalance": 0.0,
    "frozenBalance": 0.0,
    "currency": "PKR"
  }
}
```

<Tip>
  `GET /api/merchant/orders/balance` has no side effects, so it is a good way to test your credentials and signing code.
</Tip>

## Storing credentials securely

<CodeGroup>
```bash Linux/macOS
export C2C_API_KEY="mk_live_xxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx"
export C2C_SIGNING_SECRET="sksec_xxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx"
```

```powershell Windows PowerShell
$env:C2C_API_KEY="mk_live_xxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx"
$env:C2C_SIGNING_SECRET="sksec_xxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx"
```

```bash .env file
# Add .env to .gitignore
C2C_API_KEY=mk_live_xxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx
C2C_SIGNING_SECRET=sksec_xxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx
```
</CodeGroup>

<Steps>
  <Step title="Server-side only">
    Call the C2C API from your backend. Never ship the API key or signing secret to a browser or mobile app.
  </Step>
  <Step title="Use a secret manager in production">
    Azure Key Vault, AWS Secrets Manager or HashiCorp Vault, not plain configuration files.
  </Step>
  <Step title="Never log credentials">
    Mask the `Authorization` header and never log the signing secret.
  </Step>
  <Step title="Separate keys per environment">
    Use different keys for development and production. Keys only work in the environment that issued them.
  </Step>
  <Step title="Rotate on exposure">
    If a key or secret may have leaked, contact C2C to revoke it and issue a replacement.
  </Step>
</Steps>

## Account-level access controls

Besides the API key and signature, C2C applies these checks when you create an order:

| Check | Result when it fails |
|-------|----------------------|
| Merchant account is **Active** | `403`: `Merchant account is suspended; new orders are not accepted.` |
| **IP whitelist**, if C2C has enabled one for your account (Deposit / Withdrawal scope) | `403`: `IP not in whitelist.` |
| Wallet **channel enabled** for your account and order type | `422`: `JazzCash deposits are disabled for this merchant.` |

## Authentication errors

### 401 Unauthorized: API key

Returned when the `Authorization` header is missing, isn't a Bearer `mk_` key, or the key is unknown or revoked. The response has an **empty body**.

```http
HTTP/1.1 401 Unauthorized
Content-Length: 0
```

**Checklist**

1. The header is exactly `Authorization: Bearer mk_live_...`, with no quotes or extra spaces.
2. The key belongs to the environment you are calling.
3. The key has not been revoked or replaced by a regeneration.

### 401 Unauthorized: signature

Returned when the API key is valid but the request signature is missing, malformed, expired or wrong. Unlike an API key failure, this response has a JSON body with a `code`:

```json
{
  "success": false,
  "error": "Request signature is missing, malformed, expired, or invalid.",
  "code": "SIGNATURE_REQUIRED",
  "traceId": "15f1bf9c3472631576b915f2382451fd"
}
```

See [Signature error responses](/api-reference/signature-guide#signature-error-responses).
